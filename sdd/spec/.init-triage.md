# Init Triage

Items raised during `/sdd init` Import Mode that need user decisions before the spec can be considered complete. Each item is resolved interactively via `/sdd init` Resume Mode.

While any `**Status:** open` items remain, `sdd/spec/config.yml` carries `transition: true` and the PR-boundary review pipeline is suspended.

## TRIAGE-001: `lib/screens/login_screen.dart` is not referenced by `main.dart`

**Status:** open
**Target REQ:** REQ-AUTH-001 / REQ-BOOT-002
**Context:** `lib/main.dart` imports `simple_login_screen.dart` and navigates to `SimpleLoginScreen` on unauthenticated boot. `lib/screens/login_screen.dart` (625 lines) exists alongside it but is not imported from `main.dart`, `home_screen.dart`, or `settings_screen.dart`. Grep finds no inbound reference. The file appears to be a vestigial pre-refactor login implementation.
**Recommendation:** Delete `lib/screens/login_screen.dart` after confirming with the user that it is dead code. If the user wants to keep it as a reference implementation, move it under `lib/_archive/` and annotate the top of the file as legacy.

## TRIAGE-002: Shortener endpoint cascade

**Status:** open
**Target REQ:** REQ-URL-001
**Context:** `FileUploadService.shortenUrl` tries Zipline v4 (`POST /api/shorten` with `destination` + `vanity` fields), then v3 (same path, `url` + `vanity` fields), then legacy (`POST /api/upload` with `format=RANDOM`). The cascade is hard-coded with no server-version negotiation. Whether this is load-bearing back-compat (real users on Zipline v3) or vestigial cleanup-debt is unclear.
**Recommendation:** Decide the minimum supported Zipline server version. If the answer is v4, drop the v3 and legacy fallbacks (saves ~80 LOC and three failure modes). If v3 is still supported, keep the cascade and document it in `documentation/lanes/api-reference.md` as a tolerated drift.

## TRIAGE-003: `setFilePassword` is best-effort silent

**Status:** open
**Target REQ:** REQ-FILES-002 (proposed)
**Context:** `FileUploadService.setFilePassword` attempts three endpoints (`/api/user/files/:id`, `/api/files/:id`, `/api/user/files/:id/password`) and returns `false` on failure without surfacing the failure to the user. No Zipline release is known to support password-protected files via this PATCH. The UI exposes a "set password" affordance on the activity-log file detail.
**Recommendation:** If no Zipline release supports password protection on files, remove the UI affordance and the method. If support exists in a specific Zipline version, document the version in `api-reference.md` and surface failure to the user with a SnackBar.

## TRIAGE-004: `setFileExpiration` is aspirational

**Status:** open
**Target REQ:** REQ-FILES-003 (proposed)
**Context:** `FileUploadService.setFileExpiration` is documented in-code as "File expiration can only be set during upload, not modified afterward" and unconditionally returns `false`. The settings screen exposes an "expiration" control on the file detail view that calls this method. Calling the control is a no-op; the user sees no feedback.
**Recommendation:** Hide the expiration control on the file detail UI. Keep it only on the upload-time pre-flight screen where it actually works.

## TRIAGE-005: Package name is the Flutter template default

**Status:** open
**Target REQ:** REQ-BOOT-001 / CON-PLATFORM-002 (proposed)
**Context:** `android/app/build.gradle` declares `applicationId = "com.example.zipline_native_app"`. The same string appears as the MethodChannel namespace (`com.example.zipline_native_app/intent`) and is hardcoded into `cloudflare-oauth-redirect/src/worker.js` as the Android Intent URL fallback. A `TODO` comment in `build.gradle` flags the placeholder. Shipping to Play Store under `com.example.*` is impossible.
**Recommendation:** Rename to `com.zipline.app` (or another stable identifier) and update in lockstep: `build.gradle` `applicationId`, MainActivity package declaration + path, MethodChannel name, AndroidManifest `<package>`, and `worker.js` Intent URLs. The rename touches ~10 files and must land before any release build.

## TRIAGE-006: Legacy sensitive-data migration

**Status:** open
**Target REQ:** REQ-AUTH-004 (proposed)
**Context:** `AuthService._migrateSensitiveDataIfNeeded` copies `password`, `session_cookie`, `cf_client_id`, and `cf_client_secret` from `SharedPreferences` to `FlutterSecureStorage` on first call after upgrade. The migration is one-shot per process. Without a clear answer on which release first wrote those keys to plain SharedPreferences, we cannot tell whether any current user still has legacy values to migrate.
**Recommendation:** Identify the earliest pre-migration release in git history. If all live installations have already migrated (e.g., the migration shipped >12 months ago), remove the migration code in the next major version.

## TRIAGE-007: README claims "dark mode only" but light theme exists

**Status:** open
**Target REQ:** REQ-THEME-001
**Context:** `README.md` says "Dark mode: Because I'm into cybersecurity and my retinas are already damaged enough. (Also, I was too lazy to implement light mode.)". `lib/core/constants.dart` defines a complete `AppTheme.lightTheme`, `lib/providers/theme_provider.dart` supports `ThemeMode.system` / `ThemeMode.light` / `ThemeMode.dark`, and `settings_screen.dart` exposes the toggle. Either the README is out of date or the light theme is half-shipped and visually broken.
**Recommendation:** Decide whether the light theme is a supported product surface. If yes, polish it (verify every screen renders correctly under `ThemeMode.light`), update the README, and add a screenshot. If no, remove `AppTheme.lightTheme`, default `ThemeProvider` to a fixed `ThemeMode.dark`, and remove the settings toggle.
